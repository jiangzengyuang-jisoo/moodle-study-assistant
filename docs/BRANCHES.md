# 客户端发行与同步

`codex` 面向 Codex，`deepseek` 面向 DeepSeek Harness。两端分别下载、安装和验收；`client-target.json` 是随分支发布的客户端选择，setup 与诊断不会根据另一个客户端的配置宣称本端可用。通用兼容辅助代码可保留，但不会被选中分支的默认安装调用。

GitHub 默认分支为 `codex`，仓库首页与默认下载对应 Codex 版；DeepSeek Harness 用户选择 `deepseek` 分支下载。旧 `main` 分支已删除，其提交历史完整保留在两个发行分支中。

## 使用与已有部署

- 下载前选择所需分支；ZIP 应包含该分支的 `client-target.json`。
- 两端使用独立文件夹。`.private/`、`Study/`、`config.local.json`、`.codex/` 和虚拟环境不由 Git 分支隔离；不要在个人学习部署中来回切分支来切换客户端。
- 已有部署先备份，再比较源码更新。保留各自学习档案和凭据；不要整体覆盖、自动搬迁或混合两个账号的记录。
- `deepseek` 分支来自公开源码基线，不自动包含 D 盘独立部署的额外未合并修复。移植前先比较提交与实际文件，逐项验收。

## 维护分工

Codex 默认只维护本地版和公开版 `codex` 分支；DeepSeek 版本由 DeepSeek Harness 维护。只有用户明确要求 Codex 修改 DeepSeek 版本时，才可修改或同步到 `deepseek` 分支。共同功能修复不会自动授权另一分支的修改。

## 获授权后怎样同步共同修复

以下流程仅适用于用户已明确要求同步的目标分支，不要求每次修改都跨分支同步。

1. 下载、记忆、资料索引、学习状态等共同修改单独提交，不夹带客户端清单和说明。
2. 在另一个干净的源码分支上 `git cherry-pick <共同修复提交>`，处理冲突并运行相关检查。不要用整目录覆盖，也不要定期整分支合并来覆盖客户端选择。
3. 客户端配置、入口和说明只在对应分支修改。需要两端共同修复时拆成共享提交与各端适配提交。
4. 用 `git cherry` 核对待同步补丁，分别记录验证结果；配置正确不等于桌面端已运行成功。
5. 通过检查后创建本地提交。推送分支、改变默认分支、移动或删除现有部署均需明确授权。
